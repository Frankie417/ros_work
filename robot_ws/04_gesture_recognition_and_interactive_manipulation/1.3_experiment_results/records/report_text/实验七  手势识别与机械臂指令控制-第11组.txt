一、实验目标
1. 理解手势识别输出的类别、置信度及误识别问题。
2. 能够选取3—5种稳定手势作为机器人指令。
3. 利用连续帧确认和置信度阈值减少误触发。
4. 实现手势—动作映射、执行互锁及停止/复位状态管理。
二、实验重点与难点
重点：手势类别映射、连续识别去抖、状态机、BUSY锁、Five停止与Home复位。
难点：连续的识别结果与耗时的机械臂离散动作之间需要状态机解耦，避免重复启动。

0.70（模型分数与几何分数共用）

识别采样/调用间隔
每轮 tick 结束后约 100 ms 再调度
不是固定 10 FPS：单轮 = 取帧 + 推理 + 标注 + 界面刷新，实测约 6～8 FPS。窗口用 after(100, tick) 递归调度，上一轮结束才开始下一轮，天然不会堆积。
重复指令冷却策略
不做固定秒数冷却，改为每轮手动“准备下一条”
Controller.arm() 置 armed=True 且只消费一次；执行后 busy=True、armed=False，必须重新 arm 才接受新候选，因此保持 OK 不会重复下发。
BUSY期间新指令处理策略
拒绝新候选，Five 仍然有效
本机 feed() 在 busy 时直接返回 None；Jetson Engine.submit() 以 busy/stopped/epoch 三重条件拒绝。Five 走独立 /stop 通道，不受 BUSY 影响。
停止/复位触发条件
Five×2 帧、界面停止按钮、心跳超时 1.5 s、动作异常；复位为 Three+OK→home
停止：cancel 事件置位，运动线程在 trajectory_callback 与每次 set_servo_angle 前 check()，抛 Cancelled 后调用 hold()。复位：set_tool_pose('home', T=2.0, is_soft_move=True)，逆解失败即报错而不是静默返回。


4.3 系统流程与状态图
整体链路见图 1：本机只做拍摄与识别，指令经 Micro-USB gadget 网络的 HTTP 服务送到 Jetson，Jetson 用原实验 SDK 驱动 6 个舵机；端口 8765 是接收服务，8888 是 JupyterLab，两者用途不同。状态机见图 2。


图1  系统链路：本机识别 → USB 网络 HTTP → Jetson 接收 → 原 SDK → 机械臂
链路分三层：本机（Windows 11 / Python 3.11.9）负责采集、识别、去抖与指令调度；传输层是一条 Micro-USB 数据线形成的 gadget 网卡（本机侧地址 192.168.55.1）；Jetson 端只做接收、执行与制停，不装 MediaPipe、不开摄像头。停止请求与动作请求走不同的 HTTP 调用，网络层用独立的 stop_latched 事件与 epoch 计数保证“停止不被动作请求堵住”。
上电顺序上，接收端启动即处于 locked（stopped=True）状态，必须由本机先发 /clear 解除，再由界面“准备下一条”置 armed；这样即使误连也不会立刻动作。


图2  手势指令状态机与停止路径
状态迁移条件全部是“连续同标签帧数 + 阈值 + 是否已准备”，没有任何基于时间窗的猜测。SELECT 到 CONFIRM 再到 EXECUTE 在同一帧内完成，所以真机画面基本只能截到 EXECUTE 与 BUSY True，不会单独出现 CONFIRM；本报告也未伪造 CONFIRM 截图。STOPPED 是唯一会锁定后续指令的状态，解除停止（/clear）不会自动准备，仍需人工确认现场安全。

表 5-2  模块职责划分
本机侧的核心只有二十来行：去抖与状态迁移都写在 Controller.feed 里，所有“什么时候算一次手势”的判断集中在这一处，便于复现参数。
def feed(self, label, score, now=None):
    label = label if score >= self.threshold else None        # 低于阈值按无手势
    self.stop_count = self.stop_count + 1 if label == 'Five' else 0
    if not self.stopped and self.stop_count >= 2:            # Five 优先于一切
        self.stop(); return 'stop'
    if self.stopped or self.busy or not self.armed:           # 三重闸门
        return None
    self.count = self.count + 1 if label == self.last else 1  # 换标签即重计
    self.last = label
    if label is None or self.count < self.frames:
        return None
    if label in ACTIONS:                                      # 只选候选
        self.candidate, self.selected_at, self.state = label, now, 'SELECT'
    elif label == 'OK' and self.candidate:                    # 确认即执行
        self.state, self.busy, self.armed = 'EXECUTE', True, False
        return ACTIONS[self.candidate]
Jetson 侧的制停不是“发个信号就完事”：取消事件在每个运动码下发前检查，捕获 Cancelled 后用实测角度覆盖未完成的目标，并要求连续两次新鲜反馈稳定才认账。
def hold(self):
    self.allow_hold = True                     # 只放行 hold 自己的角度写入
    for identifier in self.ids:
        angle = self.query(identifier)          # 必须拿到新鲜反馈，否则抛错
        self.manager.set_servo_angle(identifier, angle, interval=0, power=0)
    while time.monotonic() < deadline:          # 1.5 s 内连续 2 次稳定
        if near_target and all(abs(current[i]-previous[i]) <= .5 ...):
            return {'hold_sent': True, 'feedback_stable': True}
    raise RuntimeError('Hold sent but stationary feedback not confirmed')
这样设计的结果是：只要反馈拿不到或不稳定，hold 就报错并把接收端置为 failed 相位，而不是给出一个“已停止”的假结论——这正是本组在测试里坚持核对 stop_phase 的原因。

六、问题与分析、展望
以下 4 个问题均为本次实验中真实遇到并已定位、解决，按“现象 → 原因 → 处理 → 复测 → 改进”完整记录，可为后续调试提供参考。
问题 1　界面提示 Invalid token，连接被拒
现象：地址填 http://192.168.55.1:8765，点“连接并查询”后状态栏显示“连接失败：Invalid token”。
原因：接收端每次启动都用 secrets.token_urlsafe(24) 现生成令牌，并用 compare_digest 比对请求头 X-Gesture-Token；沿用上一次启动的令牌（或复制时带了 TOKEN: 前缀、空格、换行）必然 401。服务本身是通的，说明网络与端口都没问题。
处理：回到 Jetson 终端复制当次 TOKEN 整串，粘贴到“令牌”框（密码框只显示星号），重新点“连接并查询”。
复测：连接成功，界面显示接收端模式 hardware、BUSY False，随后 /clear 与动作均正常。
改进：接收端可将当次令牌同步写入本地文件，由本机经同一 USB 线路读取，从根本上避免手工复制出错。
问题 2　Three 与 OK 偶发互相干扰
现象：快速摆出 Three 时偶被判为 OK，摆 OK 时偶被判为未定义手势。
原因：两者都走关键点几何规则而不是模型类别。Three 要求三指伸直且小指弯曲，OK 要求环距 ≤0.42 且三指伸直；当食指与拇指靠近、或小指没有真正弯下去时，两个判据会同时临界。
处理：把 OK 判定前置（先判环距再判 Three），并要求三指伸直比值留有余量；阈值保持 1.85/1.55/0.42 不变，改为在连续 3 帧都满足时才生效。
复测：按图 5、图 6 的标准手形摆位后可稳定区分，Three 0.764、OK 0.929 均顺利通过阈值，连续测试未再出现互串。
改进：引入手掌朝向归一化与两帧间关键点位移约束，或对 OK 单独训练一个轻量分类头。
问题 3　摄像头被占用导致取帧失败
现象：点“启动摄像头”后状态提示“摄像头无法打开”，或运行中突然“识别停止：摄像头取帧失败”。
原因：Windows 下 DSHOW 后端对同一设备是独占的，旧识别窗口、会议软件、相机应用都可能占用；USB 带宽不足时也会读帧超时。
处理：先关闭其他相机程序，再确认编号（0 为内置，1 为外接）；代码里取帧失败会 stop_camera() 并锁停止，避免带着旧帧继续下发指令。
复测：释放占用后重新启动即恢复正常，随后连续运行约 10 分钟未再出现断流。
改进：启动时枚举可用设备并给出候选列表，取帧失败自动重连 1～2 次再报警。
问题 4　心跳超时会把“拔线”变成一次制停
现象：测试中拔掉 Micro-USB 线，机械臂当场停在原姿态，本机界面同时进入停止锁定。
原因：接收端看门狗每 0.1 s 检查 last_seen，超过 1.5 s 未收到 /heartbeat 就调用 stop('USB network heartbeat lost')；这是设计行为，不是故障，但也意味着网络抖动同样会触发制停。
处理：不改逻辑，只在报告与操作规范里写明：动作过程中不要插拔数据线；恢复连接后必须重新 /clear 并重新准备。
复测：重新插线、粘贴新 TOKEN 连接后，界面显示 hardware，解除停止后可继续测试。
改进：把超时阈值做成可配置项，并在断连时保留最近 5 条事件的本地缓存，便于事后定位是抖动还是真断线。
总体分析
本次实验真正的难点不在识别，而在“把连续、会抖的视觉输出接到离散、耗时的机械动作上”。识别每 100 ms 出一帧结论，机械动作要 1～2 s 才走完，两者节拍差一个数量级，如果直接把识别结果当命令下发，一次抬手就会被拆成十几条指令。解决办法是三层解耦：帧级用阈值与几何余量筛掉低质量结论；轮次级用连续帧与 armed 标志保证“一次手势只产生一条命令”；动作级用 busy 与 epoch 保证“一条命令只执行一次、旧命令不能在新会话里复活”。
第二点体会是“停止要比执行更可靠”。停止路径若排在动作请求之后等锁，关键时刻就会失效，因此 /stop 走独立调用，接收端用 cancel 事件在运动码下发前检查，最后还要凭新鲜角度反馈确认真的停住。本组针对这条链路编写了 10 项自动测试并全部通过，覆盖停止抢占、心跳丢失取消、hold 失败不可清除等关键分支，说明逻辑层面已经闭合。
展望
· 关键点规则补强：给 Three/OK 增加手掌朝向归一化与时间连续性约束，减少临界手形的互相误判；用本次采集的截图做一个小规模验证集，量化两者的混淆率。
· 制停量化：用高速摄像或舵机角度日志测量“抬 Five → 舵机停止”的延迟与过冲角度，给出分布而不是单次观感；同时对比 hold 与直接断电的差别。
· 鲁棒性测试：补做弱光、逆光、侧向手、戴手套、双手同时入镜等场景，把“多手直接拒绝”这一策略的代价与收益量化。
· 工程化：把参数（阈值、帧数、超时）外置为配置文件并在界面显示实际生效值；增加物理停止联锁，让软件制停只作为第二道防线。
